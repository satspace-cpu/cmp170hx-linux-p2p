# CMP 170HX PCIe Gen3 / Gen4: состояние исследований

> **Статус: НЕ РЕШЕНО / только исследование.** По публичным материалам, повторно проверенным 19.08.2026, мы не нашли воспроизводимого CMP 170HX с `LnkSta: Speed 8GT/s` (Gen3) или `16GT/s` (Gen4). Изменить advertising/capability — ещё не значит реально обучить link на этой скорости.

## Короткий статус

| Поколение | Скорость | CMP 170HX |
|---|---:|---|
| Gen1 | 2.5 GT/s | Сток |
| Gen2 | 5.0 GT/s | **Работает программно** |
| Gen3 | 8.0 GT/s | **Пока не решено** — advertising получали, реальный training 8 GT/s не подтверждён |
| Gen4 | 16.0 GT/s | **Не решено** |

Не путайте поколение PCIe и ширину. Пайка 24 конденсаторов возвращает x16, но сама по себе не делает Gen3. Наш текущий проверенный вариант — Gen2 x16.

# Что уже получилось по Gen3

В экспериментах удавалось заставить endpoint показывать Gen3-совместимый capability/target state — то есть система могла выглядеть так, будто 8 GT/s разрешены.

Но ключевой факт оставался другим:

```text
LnkSta: не 8GT/s
```

В публичном архиве есть эксперимент, где target 8 GT/s принимался, но фактический link оставался на более низкой скорости. Также не было подтверждения прохождения обязательных для Gen3 фаз equalization.

Поэтому **`LnkCap: Speed 8GT/s` не считается рабочим Gen3**.

---

# Почему нельзя просто заменить Gen2 на Gen3 в текущем патче

Рабочий Gen2 использует несколько уровней:

- открывает нужные PLM через SEC2 Booter;
- меняет XP3G/XVE state;
- снимает Gen2 software-disable в `CYA_0`;
- выставляет `LINK_CONFIG_0` MAX_RATE на Gen2;
- программирует связанные overrides;
- заставляет upstream root-port выполнить retrain.

Очень важный результат исследований: Gen2 работает **даже несмотря на то, что попытка очистить fuse-sense `OPT_GEN23` на самом кристалле не проходит**. Значит настоящие рабочие рычаги Gen2 находятся не в простом переписывании fuse reflection.

Для Gen3 есть признаки дополнительного независимого ограничения.

## Известный fuse fingerprint CMP 170HX

```text
FUSE_PCIE_GEN23_DIS  0x0082057c = 0x00000001
FUSE_PCIE_GEN3_DIS   0x00820580 = 0x00000001
FUSE_PCIE_MAGIC_D    0x00820520 = 0x16680000
```

Особенно интересен отдельный `FUSE_PCIE_GEN3_DIS`.

Но отсюда **не следует**, что достаточно сделать:

```text
write 0x00820580 = 0
```

Аналогичный fuse-sense для Gen23 уже показал, что прямой write может быть физически невозможен. Поэтому это диагностический эксперимент, а не готовое решение.

# Второй слой — DevInit

В сравнении CMP 170HX и A100 найдены PCIe-релевантные отличия в данных DevInit.

Публичный разбор указывает на:

- отдельную PCIe config table внутри DevInit Falcon image;
- отличающиеся байты CMP vs A100;
- suppress flag, который пропускает часть higher-generation PCIe programming;
- XVE/write-only регистры, связанные с high-speed init sequence.

Именно поэтому наиболее серьёзная текущая гипотеза уже не выглядит как «поменять один PCI config register». Возможно, придётся менять то, **что GSP-RM/DevInit потребляет**, или воспроизводить конечное состояние, которое A100 получает во время DevInit.

Это заметно сложнее Gen2.

# Наиболее интересные направления исследований

Ниже — **не готовые инструкции**, а направления, где есть смысл копать.

## 1. Снять A/B dump A100 и CMP

На одинаковых этапах загрузки снять PCIe/XP3G/XVE state:

```text
cold boot
до GSP
после DevInit
после GSP-RM
до retrain
после retrain
```

Самый ценный вариант — физическая A100 PCIe рядом с CMP 170HX на одном типе host/root-port.

## 2. Искать не сам fuse, а место, где его результат используется

Если fuse-sense read-only, где-то дальше этот бит всё равно превращается в решение:

- разрешить/запретить Gen3;
- выставить PHY mode;
- пропустить блок DevInit;
- ограничить supported-speed vector.

Именно downstream consumer может оказаться реальным программным рычагом.

## 3. Логировать Gen3 equalization

Для Gen3 есть дополнительная PHY equalization procedure. В следующем debug-патче имеет смысл снимать:

- target speed;
- supported speeds vector;
- LTSSM state;
- Equalization Phase 1/2/3 и complete bits;
- XP3G rate/override;
- AER до и после retrain.

Если карта пытается перейти в Gen3 и падает обратно — это один класс проблемы. Если equalization вообще никогда не начинается — другой.

## 4. GSP-RM / DevInit in-memory experiment

Публичные исследования всё сильнее указывают на GSP-RM/DevInit layer.

Более разумный порядок:

1. понять consumer и данные;
2. попробовать runtime/in-memory substitution;
3. только потом думать о permanent SPI modification.

Сразу шить flash ради Gen3 сейчас — плохая первая стратегия.

## 5. Расширить уже рабочую Gen2 instrumentation

Нам не нужно начинать с нуля. Текущий Gen2 path уже умеет открыть PLM и логировать большой набор PCIe регистров. Следующий Gen3 debug лучше строить поверх него и сначала **только читать/логировать**, а не сразу писать десятки неизвестных значений.

# Что будет считаться настоящим успехом

Нужно показать:

```bash
sudo lspci -vv -s <GPU_BDF> | grep -E 'LnkCap:|LnkSta:|LnkCtl2:|LnkSta2:'
```

и обязательно:

```text
LnkSta: Speed 8GT/s
```

После этого ещё нужны:

1. несколько cold boot с повторным Gen3 training;
2. host↔GPU bandwidth, соответствующий более быстрому link;
3. P2P bandwidth при двух картах;
4. отсутствие AER ошибок под длительной передачей;
5. точная topology motherboard/root-port;
6. версии kernel/NVIDIA;
7. полный patch/commit.

Для нашей физически переделанной x16 карты подтверждённый **Gen3 x16** был бы особенно интересен, но bandwidth сам по себе не доказательство — `LnkSta` обязателен.

# Безопасность

- Держите рабочее ядро/драйвер в GRUB как fallback.
- Делайте backup всего постоянного состояния до эксперимента.
- Сначала runtime/in-memory, потом flash.
- Меняйте по одному блоку регистров.
- Постоянно сохраняйте `dmesg` и AER.
- Никогда не называйте Gen3 успешным только по `LnkCap`/`LnkCtl2`.

# Что нашлось на 19.08.2026

Мы заново просмотрели публичный GitHub и веб по CMP 170HX + Gen3.

Итог интересный:

- **наработок действительно много**;
- причины ограничения уже разобраны довольно глубоко;
- advertising 8 GT/s уже удавалось получить;
- обнаружены отдельный Gen3 fuse fingerprint и DevInit differences;
- но **нового публичного воспроизводимого `LnkSta: Speed 8GT/s` мы пока не нашли**.

То есть слух «Gen3 уже копают» — абсолютно верный. А вот «Gen3 уже разлочили» — по найденным публичным данным пока нет.

Если появится новая ветка, лог или скрин с реальным `LnkSta: Speed 8GT/s`, добавим сюда и попробуем воспроизвести на наших картах.
